# Solo Shop — 個人向けオリジナルECサイト

個人が一人で運営する小さなお店（ハンドメイド作家、個人事業主など）が、自分自身で安心・簡単に運用できる規模で実装したフルスタックECプラットフォームです。クーポン・複数管理者・多段階カテゴリといった大規模事業者向けの機能は思い切って省き、商品出品・注文管理・在庫管理といったコア機能に絞っています。

- 要件定義書: [`docs/requirements.md`](docs/requirements.md)
- バックエンド: Node.js / Express / TypeScript / Prisma / PostgreSQL
- フロントエンド: 素のHTML / CSS / JavaScript（ES Modules。配信にビルド不要）
- 認証: JWT（アクセストークン + リフレッシュトークン）

フロントエンドは外部CDNに一切依存しません。CSSは生成済みのものをリポジトリに含めているため、配信するだけで動きます（詳細は「スタイル(CSS)の変更」を参照）。

## 主な機能

- 会員登録・ログイン・プロフィール・複数配送先住所管理・パスワード再設定
- 商品検索・絞り込み・並び替え・カテゴリ（1階層のフラット構造）・在庫僅少バッジ
- 商品写真のアップロード（スマホから直接。撮影場所の記録は自動で除去）
- カート・チェックアウト・決済（クレジットカード / PayPay / WeChat Pay / 代金引換。決済代行はKOMOJU）
- 注文管理（支払い待ち→支払済み→発送済み→受取完了[購入者自身で確認可能]→レビュー投稿、キャンセル/返金）
- 配送の追跡（発送時に配送業者と追跡番号を記録。購入者は注文詳細と発送メールから追跡ページへ）
- レビュー・評価、お気に入り
- 管理画面（店主本人のみアクセス可能。ダッシュボード、商品/カテゴリ/注文/会員/レビュー管理）
- メール通知（注文が入ったら店主へ、注文確認・発送のお知らせは購入者へ）
- 特定商取引法に基づく表示ページ（個人事業主向けの記載例つき。フッターから常時アクセス可）
- スマホ対応（店主も購入者も、出品から発送・受取確認まで携帯電話だけで完結）

詳細は要件定義書を参照してください。

## ディレクトリ構成

```
NanGe_ECsite/
├── package.json            # ルート。npm workspaces で backend/frontend をまとめて操作する
├── .devcontainer/          # Codespaces / Dev Container の設定（PostgreSQL込みで自動構築）
├── docs/requirements.md   # 要件定義書
├── deploy/                 # 本番運用の設定（nginx / systemd / バックアップ）
├── backend/                # Express API サーバー
│   ├── prisma/schema.prisma
│   ├── prisma/seed.ts
│   └── src/
└── frontend/                # 素のHTML/CSS/JavaScriptによるマルチページサイト
    ├── *.html               # 購入者向け画面（トップ、商品一覧/詳細、カート、注文 等）
    ├── admin/*.html         # 管理画面（店主専用）
    ├── assets/js/           # ESモジュール（API通信・共通レイアウト・各画面ロジック）
    ├── assets/css/          # 共通スタイル
    └── server.js            # 依存パッケージ不要の開発用静的サーバー
```

本番はコンテナ基盤（Docker等）を使わず、Node.js / PostgreSQLをサーバーに直接インストールして動かす構成です（`deploy/` 参照）。開発環境については、Codespaces / Dev Container を使えばPostgreSQL込みで自動構築され、自分のPCに直接入れる方法も選べます。`backend/` と `frontend/` は npm workspaces でまとめられており、依存パッケージのインストールと起動はリポジトリ直下から一括で行えます。

## セットアップ（開発環境）

### いちばん簡単な方法: GitHub Codespaces

このリポジトリには Dev Container の設定（`.devcontainer/`）が入っています。GitHubのページから **Code → Codespaces → Create codespace** を選ぶだけで、PostgreSQLの用意・依存パッケージのインストール・データベースの作成・サンプルデータの投入まで自動で終わります。**自分でPostgreSQLを入れる必要も、`sudo` を使う必要もありません。**

準備が終わったら、起動するだけです。

```bash
npm run dev
```

5173番ポートの転送URLがブラウザで開きます。**「ポート」パネルで 4000番も 5173番と同じ可視性（Public）にしてください。** 購入者向けサイトはブラウザから4000番のAPIを直接呼ぶため、片方だけ非公開だとログインできません。

以下は、自分のPCに直接入れて動かす場合の手順です。

### 1. PostgreSQLを用意

```bash
# 例: ローカルPostgreSQLにDB/ユーザーを作成
createuser soloshop --pwprompt
createdb soloshop -O soloshop
```

### 2. 依存パッケージのインストール

リポジトリ直下（このファイルがある場所）で一度だけ実行します。`backend` と `frontend` 両方の依存パッケージがまとめてインストールされ、Prisma Client も自動生成されます（`backend` の `postinstall` フックによる）。

```bash
npm install
```

### 3. バックエンドの設定とマイグレーション

```bash
cp backend/.env.example backend/.env   # 必要に応じて値を編集（DATABASE_URL, JWTシークレット等）
npm run prisma:migrate:dev             # マイグレーション適用
npm run seed                           # サンプルデータ投入（店主/デモ会員/商品/カテゴリ）
```

### 4. 起動

```bash
npm run dev                  # backend(:4000) と frontend(:5173) を同時に起動する
```

`frontend/assets/js/config.js` は、5173番ポートで開いているときだけ開発用バックエンド（`http://localhost:4000/api`）を見るようになっているため、そのまま動きます。バックエンドの `CORS_ORIGIN` も既定の `http://localhost:5173` のままで構いません。

#### GitHub Codespaces / Gitpod など、クラウド開発環境で開く場合

`localhost` に直接アクセスできず、ポート番号をホスト名に埋め込んだ転送URL（例: `https://foo-5173.app.github.dev`）を経由してブラウザからアクセスする環境では、追加の設定なしで動くように以下の対応をしてあります。

- `frontend/assets/js/config.js` は、ホスト名に含まれる `5173` を `4000` に置き換えたURLをバックエンドとして自動的に使う（例: `https://foo-5173.app.github.dev` → `https://foo-4000.app.github.dev`）
- バックエンドのCORSは、開発時（`NODE_ENV=production` でないとき）は送信元をそのまま許可する。転送URLは起動のたびに変わり得るため、`CORS_ORIGIN` を毎回設定しなくてよいようにしている（本番ではこの緩和は行わず、`CORS_ORIGIN` の許可リストのみを厳密に見る）

ブラウザから4000番ポート（バックエンド）にも5173番ポート（フロントエンド）と同様にアクセスできるよう、環境側でポートを公開設定にしてください（Codespacesの場合は「ポート」パネルで両方のポートを Public にするか、少なくとも同じ可視性に揃える）。

片方だけ起動したい場合や、個別にコマンドを実行したい場合は、ワークスペース名を指定するか該当ディレクトリに `cd` してください。

```bash
npm run dev:backend          # backendのみ（tsx watch）
npm run dev:frontend         # frontendのみ（静的配信）
npm test                     # backendのテスト一式（vitest）
npm run seed -w backend      # -w <ワークスペース名> でその workspace 内のスクリプトを実行
cd backend && npm run mail:check   # cd してから直接実行してもよい
```

### スタイル(CSS)の変更

`frontend/assets/css/style.css` は Tailwind CSS から生成済みのファイルで、リポジトリにコミットされています。**サイトを動かすだけならビルドは不要**です。

配色を変えたい、または新しいTailwindのクラス名を使い始めたときだけ、再生成してください。

```bash
npm run build:css    # tailwind.config.js と assets/css/tailwind-src.css から style.css を再生成
```

配色は `frontend/tailwind.config.js` の `brand` を編集します。共通のボタン・入力欄・カードの見た目は `frontend/assets/css/tailwind-src.css` にまとまっています。

### 公開前に書き換えるページ

以下の3ページはテンプレートです。**【 】内を実際の情報に置き換えてから公開してください。**

| ファイル | 内容 |
|---|---|
| `frontend/legal.html` | 特定商取引法に基づく表示（通信販売を行う場合は法定の表示事項） |
| `frontend/privacy.html` | プライバシーポリシー |
| `frontend/terms.html` | 利用規約 |

さらに、**SNSやチャットにリンクを貼ったときのカード表示（OGP）に使うドメインも書き換える必要があります。** フロントエンドはビルドを挟まない静的HTMLで、ドメインは実際に公開するまで分からないため、全18ページの `og:url` と `og:image` に仮のドメイン `https://shop.example.com` を入れてあります。次のコマンドで一括置換してください（実際のドメインが `https://my-shop.jp` の場合の例）。

```bash
sed -i 's|https://shop.example.com|https://my-shop.jp|g' frontend/*.html
```

カードに使う画像は `frontend/assets/img/ogp.png`（1200×630px）です。ロゴと店名だけの汎用デザインのため、そのまま使えますが、店の雰囲気に合わせて差し替える場合は同じサイズ・比率（1200×630px、PNG）を保ってください。フロントはSSRを行わないため、**商品ごとに違う画像を出すことはできません**（商品詳細ページをシェアしても、この共通画像が表示されます）。

プライバシーポリシーの本文は、**このサイトが実際に取得・保存・委託している情報にあわせて記載してあります**（会員情報、注文の記録、決済代行・メール送信・配送業者への委託、ブラウザに保存する情報など）。運営方法を変えた場合は、記載も合わせて見直してください。

利用規約の第5条には、**支払いのないご注文を自動的に取り消す時間**を記載しています。`PAYMENT_HOLD_MINUTES` を変更した場合は、規約の記載も必ず合わせてください（記載と実際の動作が食い違うとトラブルの原因になります）。第6条の送料も同様です。

これらは法令に関わる内容のため、公開前に専門家の確認を受けることをおすすめします。

## 本番運用

1台のサーバー（月1,000円程度のVPSで十分）に、次の3つを置く構成を想定しています。設定ファイルは `deploy/` にあります。

```
インターネット
   │  HTTPS
   ▼
 nginx  ── 購入者向けサイト（frontend/ の静的ファイル）を配信
   │    └ /api と /uploads は下のNode.jsへ渡す
   ▼
 Node.js（systemdで常時起動。落ちても自動で復帰）
   │
   ▼
 PostgreSQL
```

| ファイル | 役割 |
|---|---|
| `deploy/nginx.conf.example` | HTTPS・静的配信・APIへの転送 |
| `deploy/soloshop-api.service` | APIを常時起動させる（systemd） |
| `deploy/backup.sh` / `deploy/restore.sh` | バックアップと復元 |
| `deploy/soloshop-backup.service` / `.timer` | 毎日のバックアップ |

### 1. 置く・動かす

```bash
sudo mkdir -p /var/www/soloshop && sudo chown -R $USER /var/www/soloshop
git clone <このリポジトリ> /var/www/soloshop
cd /var/www/soloshop

cp backend/.env.example backend/.env   # 中身を本番用に書き換える（次の項目を参照）
npm ci                     # backend/frontend の依存パッケージをまとめてインストール
npm run build              # backend/dist/ を作る
npm run prisma:migrate     # データベースの構造を作る・更新する
npm run seed                # 最初の1回だけ。店主アカウントとサンプル商品が入る
```

### 2. `.env` で必ず書き換えるもの

```bash
NODE_ENV="production"
DATABASE_URL="postgresql://soloshop:強いパスワード@localhost:5432/soloshop?schema=public"

# 秘密鍵は必ず作り直す（設定例のままだと、誰でも管理者になりすませます）
JWT_ACCESS_SECRET="openssl rand -base64 48 で作った値"
JWT_REFRESH_SECRET="openssl rand -base64 48 で作った別の値"

SITE_URL="https://shop.example.com"        # メールに載せるリンクの基点
PUBLIC_API_URL="https://shop.example.com"  # 商品写真のURLの組み立てに使う
CORS_ORIGIN="https://shop.example.com"
TRUST_PROXY=1                              # nginxを前に置くため必須（下記参照）
```

`PUBLIC_API_URL` の設定漏れには特に注意してください。**間違ったURLのままアップロードした商品写真は、そのURLごとデータベースに保存されるため、後から設定を直しても直りません。**

本番として起動すると、これらの設定は起動時に点検されます。秘密鍵が設定例のままなら**起動しません**。その他の設定漏れは警告として表示されます。

```
[設定エラー] JWT_ACCESS_SECRET が設定例のままです。誰でも管理者になりすませる状態のため起動を中止します。
[設定の確認] PUBLIC_API_URL が開発用のままです。この状態でアップロードした商品写真は、購入者から見えないURLで保存されます
```

### 3. 常時起動させる（systemd）

ターミナルで `npm start` したままにすると、接続を切った時点で店が閉まってしまいます。サーバーの再起動後も自動で立ち上がるよう、systemd に任せます。

```bash
sudo cp deploy/soloshop-api.service /etc/systemd/system/
sudo nano /etc/systemd/system/soloshop-api.service   # ユーザー名・パス・nodeの場所を自分の環境に合わせる
sudo systemctl daemon-reload
sudo systemctl enable --now soloshop-api

sudo systemctl status soloshop-api    # 動いているか
sudo journalctl -u soloshop-api -f    # ログを見る
```

### 4. HTTPSで公開する（nginx + Let's Encrypt）

**HTTPSは必須です。** 平文のHTTPでは、ログインのパスワードも住所も、通信経路の途中で読まれます。証明書は無料で取得でき、更新も自動化できます。

```bash
sudo apt install nginx certbot python3-certbot-nginx

sudo cp deploy/nginx.conf.example /etc/nginx/sites-available/soloshop
sudo nano /etc/nginx/sites-available/soloshop     # ドメイン名とパスを書き換える
sudo ln -s /etc/nginx/sites-available/soloshop /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

sudo certbot --nginx -d shop.example.com          # 証明書を取得（更新は自動）
sudo systemctl status certbot.timer               # 自動更新が有効か確認
```

購入者向けサイトとAPIを同じドメインで配信するため、`frontend/assets/js/config.js` の書き換えは不要です（同じドメインの `/api` を見るようになっています）。

設定に含めている要点:

- **HTTPは自動でHTTPSへ転送**し、証明書の更新に使う経路だけは転送しない
- **`client_max_body_size 6m`** — 既定の1MBのままだと、商品写真のアップロードが途中で切られます
- HTMLとJS/CSSは毎回更新を確認させ、**サイトを更新したのに古い画面が表示され続ける事故を防ぐ**（変わっていなければ通信量はほぼゼロです）
- HSTS などのセキュリティヘッダ

**`TRUST_PROXY=1` を `.env` に設定してください。** nginxを前に置くと、設定しない限り全ての訪問者が同じIPアドレス（nginx自身）として扱われます。レート制限は本来「訪問者ごと」にかかりますが、この状態では**サイト全体で1つの枠を共有**することになり、アクセスが集中したときに訪問者全員が閲覧できなくなります。

逆に、Node.jsをインターネットに直接公開している場合は未設定のままにしてください。設定すると、リクエストヘッダを詐称してレート制限を回避されます。

### 5. バックアップ（最重要）

失うと取り返しがつかないものが2つあります。**両方を一緒に**保存してください。

1. **データベース** — 注文・会員・商品。消えると売上の記録ごと無くなります
2. **`backend/uploads/`** — 商品写真。撮り直しがきかないものもあります

```bash
sudo mkdir -p /var/backups/soloshop && sudo chown $USER /var/backups/soloshop
./deploy/backup.sh                 # 手動で1回
BACKUP_DIR=/mnt/usb ./deploy/backup.sh   # 保存先を変える
```

毎日自動で取るには、systemdのタイマーを使います（既定で毎日3:30、14日分を保持）。

```bash
sudo cp deploy/soloshop-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now soloshop-backup.timer
systemctl list-timers soloshop-backup    # 次回の実行予定
```

**保存先はこのサーバーの外にも置いてください。** 同じディスクに置いたバックアップは、ディスクが壊れたときに一緒に失われます。外付けディスクや、別のサーバー・クラウドストレージへ定期的にコピーしてください。

#### 戻し方

```bash
./deploy/restore.sh                  # 保存されている一覧を表示（何も壊しません）
./deploy/restore.sh 20260813-033000  # その時点に戻す
```

**バックアップは「戻せて初めて」バックアップです。** 本番で慌てて初めて試すことにならないよう、一度は練習してください。練習用の別のデータベースへ戻せば、本番に触れずに確かめられます。

```bash
sudo -u postgres createdb soloshop_restore_test
TARGET_DATABASE_URL="postgresql://soloshop:パスワード@localhost:5432/soloshop_restore_test" \
  UPLOAD_DIR=/tmp/restore-test ./deploy/restore.sh 20260813-033000
```

### 消費税とインボイス（適格請求書）

価格はすべて**税込**で登録・表示します（消費者向けの総額表示）。商品ごとに消費税率を選べます。

| 税率 | 対象 |
|---|---|
| 10%（標準税率） | 通常の商品 |
| 8%（軽減税率） | 飲食料品（酒類・外食を除く） |

税率は管理画面の商品登録・編集から選択します。送料は標準税率10%として計算します。

お支払いが済んだ注文は、購入者が注文詳細から**領収書を表示・印刷（PDF保存）**できます。税率ごとに区分した金額と消費税額が記載されます。

#### 適格請求書として発行する場合

適格請求書発行事業者の登録を受けている場合のみ、`backend/.env` に登録番号を設定してください。

```bash
INVOICE_ISSUER_NAME="【氏名または屋号】"
INVOICE_REGISTRATION_NUMBER="T1234567890123"
```

設定すると書類が「適格請求書（領収書）」として発行され、登録番号が記載されます。

**免税事業者の方は `INVOICE_REGISTRATION_NUMBER` を設定しないでください。** 登録を受けていない事業者が適格請求書を発行することは認められていません。未設定の場合は「領収書」として発行され、適格請求書ではない旨が自動的に明記されます（税率ごとの内訳は参考として表示されます）。

なお、消費税の端数処理は**税率ごとに、書類1枚につき1回**行っています。これはインボイス制度で定められた方法です。

### 送料（地域別）

宅配便の実費は届け先で変わるため、地域ごとに設定しています。

| 地域 | 送料 |
|---|---|
| 本州・四国 | ¥500 |
| 九州 | ¥700 |
| 北海道 | ¥900 |
| 沖縄 | ¥1,200 |

**¥5,000以上のご購入は、地域にかかわらず送料無料**です（地域ごとに無料条件を変えると購入者に分かりにくいため）。

金額や区分を変えるときは、次の2ファイルを**同じ内容に**してください。値がずれると、画面の表示と実際の請求額が食い違います。

- `backend/src/config/shipping.ts`（注文時に確定する金額）
- `frontend/assets/js/shipping.js`（画面に表示する金額）

変更後は `frontend/legal.html`（特定商取引法に基づく表示）と `frontend/terms.html`（利用規約 第6条）の記載も合わせてください。

#### 扱う商品の値段が高いときは、送料無料の基準額を見直してください

いちばん安い商品が ¥5,000 以上だと、**何を1点買っても必ず送料無料**になります。送料は全額がお店の負担になりますが、金額の計算自体は正しく行われるため、画面のどこにも異常は出ません。気づかないまま続けると、利益がじわじわ削られていきます。

たとえば ¥5,200〜¥9,800 の服だけを扱う店で売上30万円まで販売を再現したところ、32件すべてが送料無料になり、**¥22,900（売上の7.6%、1注文あたり平均 ¥716）を店主が負担**していました。北海道・沖縄への発送が多いほど負担は大きくなります。

この状態になると管理画面のダッシュボードに注意書きが出ます。扱う商品の値段に合わせて `FREE_SHIPPING_THRESHOLD` を引き上げるか、送料込みの価格設定に切り替えてください。

### 商品写真について

管理画面の商品登録・編集から、スマートフォンや PC の写真をそのままアップロードできます（JPEG / PNG / GIF / WebP、1枚5MBまで）。1枚目が一覧などで使われる代表写真になります。

- サンプルデータの商品には写真が入っていません（外部の画像サービスに頼ると、その事業者が落ちたときや社内の通信制限で外部へ出られないときに、店が「画像が壊れた状態」で表示されるため）。写真を入れるまでは「画像はまだありません」の絵が表示されます
- 登録した写真が読み込めなかった場合も、壊れた画像の印ではなく同じ絵に差し替わります
- 保存先は既定で `backend/uploads/`。**バックアップの対象に含めてください**（この中身が消えると商品写真がすべて失われます）
- 保存先を変えるときは `UPLOAD_DIR`、APIサーバーを別ドメインで公開するときは `PUBLIC_API_URL` を設定します
- **スマートフォンの写真に含まれる撮影場所などの記録（EXIF）は、保存時に自動で取り除かれます。** 自宅で撮影した写真から住所が推測される事故を防ぐためです
- 中身が画像であることを先頭バイトで確認し、スクリプトを埋め込める SVG は受け付けません

### 発送と追跡番号

管理画面の注文詳細で「発送済みにする」を押すと、確定の前に配送業者と追跡番号の入力欄が出ます。ここで控えた内容は、購入者の注文詳細ページと発送のお知らせメールに、配送業者の追跡ページへのリンクつきで表示されます。

- **追跡番号は任意です。** 定形外郵便のように追跡番号が出ない発送方法もあるため、空欄のままでも発送できます（その場合、購入者側には追跡の案内を出しません）
- 対応している配送業者はヤマト運輸・日本郵便・佐川急便と「その他」です。「その他」は番号だけを購入者に伝え、リンクは出しません
- 追跡ページのURLは配送業者の都合で変わることがあります。開かなくなったときは `backend/src/config/carrier.ts` と `frontend/assets/js/carrier.js` の**両方**を同じ内容に直してください（メール用と画面用でそれぞれ参照しています）

### 支払われなかった注文の在庫

注文が確定した時点で在庫を確保するため、決済ページで離脱された注文をそのままにすると、その商品は在庫があるのに買えない状態が続きます。**一定時間（既定60分）支払いのない注文は自動的に取り消し、在庫を売り場へ戻します**（`PAYMENT_HOLD_MINUTES` で変更可）。

- 代金引換は商品と引き換えに支払う約束なので、この対象外です
- 決済ページの有効期限は自動的に保持時間の半分になり、在庫を戻した後に支払われることを防ぎます
- 万一、取り消し済みの注文に入金が届いた場合は、返金の要否を判断できるよう店主にメールで通知します

### 決済（クレジットカード・PayPay・WeChat Pay）の設定

決済代行の [KOMOJU](https://komoju.com/) を利用します。購入者はKOMOJUの決済ページで支払うため、**カード番号がこのサイトを通ることはありません**。

1. KOMOJUに加盟店登録し、使いたい決済手段を有効にする（個人事業主でも申込可能。審査があります）
   - **決済手段ごとに個別の審査・有効化が必要です。** 管理画面で有効になっていない手段を選ぶと、購入者は決済ページでエラーになります
   - WeChat Payは主に中国からのお客様向けの手段です。利用には購入者側にWeChat Payのアカウントが必要で、日本国内のお客様が使えるとは限りません
2. `backend/.env` にキーを設定する

```bash
KOMOJU_SECRET_KEY="sk_live_******"     # KOMOJU管理画面のシークレットキー
KOMOJU_WEBHOOK_SECRET="******"         # Webhook設定画面で発行される署名用の秘密鍵
SITE_URL="https://shop.example.com"    # 決済後の戻り先に使う購入者向けサイトのURL
```

3. KOMOJUの管理画面で、Webhookの送信先に次を登録する

```
https://<バックエンドの公開URL>/api/webhooks/komoju
```

送信するイベントは `payment.captured` と `payment.refunded`（任意で `payment.failed` / `payment.expired` / `payment.cancelled`）です。

#### 支払いが確定する仕組み

**注文を「支払い済み」にするのは、KOMOJUから届く署名付きの通知だけ**です。購入者のブラウザからの申告では支払い済みになりません。これにより、実際には入金がないまま商品を発送してしまう事故を防いでいます。

- 署名が一致しない通知、本文が改ざんされた通知は拒否します
- 通知された金額が注文額と違う場合は反映しません
- 同じ通知が繰り返し届いても二重に処理しません
- オンライン決済の注文は、入金が確認できるまで管理画面から発送できません

`KOMOJU_SECRET_KEY` が未設定の場合、購入者が支払いに進もうとするとエラーになります（注文は「支払い待ち」で残ります）。**設定前に無料で注文が成立してしまうことはありません**。

#### 代金引換について

代金引換はKOMOJUを経由しないため、決済の設定なしで利用できます。注文は「支払い待ち」のまま発送でき、管理画面の注文詳細に「配達時に集金してください」と表示されます。

#### 返金

管理画面で「返金済みにする」を押すとKOMOJUへ返金を依頼します。ステータスが実際に「返金済み」になるのは、返金完了の通知を受け取った時点です（依頼しただけで返金済みと表示されることはありません）。

### メール通知の設定

注文が入ったことに気づけるよう、以下のメールを自動送信します。

| タイミング | 宛先 | 内容 |
|---|---|---|
| 注文確定 | 購入者 | ご注文内容の控え |
| 支払い完了 | 店主 | 新しいご注文（発送のお願い） |
| 発送 | 購入者 | 発送のお知らせ（追跡番号と追跡ページのURLつき） |
| パスワード再設定の申請 | 申請者 | 再設定リンク |

`backend/.env` に SMTP の設定を書くと送信が有効になります。

```bash
SMTP_HOST="smtp.example.com"
SMTP_PORT=587
SMTP_SECURE=false                     # ポート465(SSL)を使う場合のみ true
SMTP_USER="******"
SMTP_PASS="******"
MAIL_FROM="Solo Shop <shop@example.com>"
SITE_URL="https://shop.example.com"   # メール本文に載せるリンクの基点
# MAIL_REPLY_TO="owner@example.com"   # 購入者が返信したときの宛先。未設定なら OWNER_EMAIL
# OWNER_EMAIL="owner@example.com"     # 注文通知の宛先。未設定なら店主アカウントのアドレス宛
```

`SMTP_HOST` と `MAIL_FROM` が未設定の間は送信されず、内容がサーバーのログに出力されます。設定前でも注文や購入は通常どおり動くため、後から設定して構いません。

メール送信は注文処理とは切り離してあり、**メールサーバーが落ちていても注文・支払い・発送は成功します**（送信失敗はログにのみ記録されます）。

店主宛の注文通知には購入者のアドレスが返信先として入っているため、メールソフトでそのまま返信すれば購入者に届きます。

### メールが迷惑メールにならないための設定（SPF / DKIM / DMARC）

**送信設定を済ませただけでは、注文確認メールは購入者に届かないことがあります。** 差出人のドメインが本当に自分のものかを受信側が確かめる仕組みがあり、その設定（DNSレコード）が無いメールは迷惑メールに振り分けられるか、そもそも受け取ってもらえません。Gmail と Yahoo! メールは2024年から、この確認を通らないメールの受け取りを制限しています。**購入者の大半はこのどちらかを使っています。**

届かなくても送信側にはエラーが出ないため、気づかないまま「注文したのに連絡が来ない」という状態が続きます。**公開前に必ず設定してください。**

#### 確認コマンド

```bash
npm run mail:check                      # 設定とDNSレコードを確認する
npm run mail:check -- you@example.com   # 実際にテストメールを送る
```

差出人ドメインのSPF・DKIM・DMARCを実際にDNSで引いて、足りないものと直し方を日本語で表示します。テスト送信では、Gmail など普段使っているアドレスを指定して、受信トレイに入るか（迷惑メールフォルダに入らないか）を必ず自分の目で確かめてください。

#### 3つの設定の役割

| | 何をするもの | 設定する場所 |
|---|---|---|
| **SPF** | このドメインのメールを送ってよいサーバーを宣言する | ドメインのDNS（TXTレコード） |
| **DKIM** | メールに電子署名を付け、途中で改ざんされていないことを示す | 送信サービスの管理画面＋DNS |
| **DMARC** | SPF/DKIMが通らなかったメールをどう扱うかを指示し、結果の報告を受け取る | ドメインのDNS（TXTレコード） |

#### 手順

**1. 差出人を自分のドメインにする**

```bash
MAIL_FROM="Solo Shop <shop@あなたのドメイン>"   # ○
MAIL_FROM="Solo Shop <あなた@gmail.com>"       # ✗ 拒否・迷惑メール扱いになる
```

Gmail や Yahoo! メールのアドレスを差出人にすると、そのドメインの持ち主（Google や Yahoo!）が定めたルールに違反するため、受信側で弾かれます。ドメインを持っていない場合は、まずお店のドメインを取得してください。

**2. 送信サービスを使う**

自宅や普通のサーバーから直接メールを送ると、そのIPアドレスに送信の実績がないため、設定を整えても迷惑メール扱いされやすくなります。個人店では、SPFとDKIMの設定を案内してくれる送信サービス（Amazon SES、SendGrid、Resend、さくらのメールボックスなど、月数百円〜無料枠あり）を使うのが確実です。`SMTP_HOST` などにその接続情報を設定します。

**3. DNSに3つのレコードを追加する**

SPFとDKIMの具体的な値は、使う送信サービスの管理画面に表示されます。DMARCは自分で決めます。

```
# SPF（ドメインのTXTレコード。1件だけ。複数あると認証が失敗します）
v=spf1 include:送信サービスが指定する値 ~all

# DKIM（送信サービスが指定するTXTまたはCNAMEレコード）
セレクタ._domainkey.あなたのドメイン

# DMARC（_dmarc.あなたのドメイン のTXTレコード）
v=DMARC1; p=none; rua=mailto:あなたのアドレス
```

**4. DMARCを段階的に強める**

最初は `p=none`（監視のみ）で始めます。`rua=` に指定したアドレスへ認証結果の報告が日次で届くので、1〜2週間ほど自分の送信がすべて認証を通っていることを確かめてから、`p=quarantine`（迷惑メール送り）→ `p=reject`（受信拒否）と強めてください。**いきなり `p=reject` にすると、設定漏れがあった場合に自分のメールがすべて届かなくなります。**

#### よくあるつまずき

- **SPFレコードを2件書いてしまう** — 複数あると認証は無条件で失敗します。1件にまとめてください（`npm run mail:check` が検出します）
- **`include:` を足しすぎる** — SPFはDNS参照10回までという上限があり、超えると失敗します（`npm run mail:check` が入れ子も含めて数えます）
- **`~all` を書き忘れる／`+all` にする** — どのサーバーからの送信も許可することになり、なりすまし対策になりません
- **ドメインを変えたのに設定を直し忘れる** — 送信サービスやドメインを変えたときは、もう一度 `npm run mail:check` を実行してください

## テスト

```bash
npm test                        # vitest + supertest によるAPIテスト
npm run lint                    # backend(TypeScript) と frontend(JavaScript) の静的検査
npm run lint:fix                # 自動で直せるものを直す
cd backend && npx tsc --noEmit  # 型チェック
```

フロントエンドはビルドを挟まず、素のHTML/JavaScriptをそのままブラウザへ配る作りです。そのぶん、変数名の書き間違いや import の書き忘れを見つける手段が `npm run lint` しかありません。**フロントエンドを触ったら必ず実行してください。**

実際、`getErrorMessage` の import 漏れが5ファイルに残っており、カートの数量変更などが失敗したときにエラー処理そのものが落ちて、購入者に何も表示されない状態になっていました（テストも型チェックもすり抜けていました）。

画面の見た目や操作感は自動では確かめられないため、`npm run dev` でサーバーを起動し、ブラウザで主要な画面・操作を確認してください。

## セキュリティ設計の要点

- パスワードは bcrypt でハッシュ化して保存
- JWT（アクセス短命 + リフレッシュ）による認証、フロントエンドのfetchラッパーで401時に自動リフレッシュ
- 全APIエンドポイントでZodによる入力バリデーション
- Prisma ORMによりSQLインジェクションを防止
- Helmet + CORS許可オリジン限定 + 認証系・注文系レート制限
- 管理者（店主）APIはRBACミドルウェア (`requireAdmin`) で保護
- **会員の凍結はその場で効きます。** 認証のたびにアカウントが有効かを確認するため、凍結した会員は手元にトークンが残っていても操作できません（迷惑行為をする相手に、トークンの期限が切れるまで注文を続けられないようにするため）
- 届け先の都道府県は47都道府県の一覧から選ぶ方式で、郵便番号（7桁）と電話番号（数字10桁以上）も形式を確認します。表記ゆれで送料の地域区分を取り違えたり、発送できない住所が登録されたりするのを防ぎます
- パスワード再設定トークンはハッシュ化保存・30分有効・使い切り。アカウント有無に関わらず同一レスポンスとしユーザー列挙を防止
- バックエンドは `/api/health`（liveness）と `/api/health/ready`（DB疎通込みreadiness）を提供し、未捕捉例外はログ出力の上で安全にプロセスを終了

## 個人向けに簡素化したポイント

小〜中規模事業者向けの元プラットフォームから、個人が一人で運営することを前提に以下を大胆に簡素化しています。

- **クーポン機能を廃止**: 発行・取得・チェックアウト適用・新規登録特典の自動付与を全て削除し、注文金額計算をシンプルに保っています。
- **管理者は店主一人を想定**: 複数管理者の作成・権限管理機能は設けていません（`ADMIN`ロールは seed で1件のみ作成）。
- **カテゴリはフラットな1階層のみ**: 大分類/中分類のツリー構造を廃止し、管理画面もシンプルな一覧+追加/削除のみにしています。
- **バナー管理を廃止**: トップページの管理者用カルーセル管理機能を削除し、静的なウェルカムメッセージに置き換えています。
