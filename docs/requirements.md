# 要件定義書 — 個人向け小規模ECサイト「Solo Shop」

## 0. 文書情報
| 項目 | 内容 |
|---|---|
| プロジェクト名 | Solo Shop（個人向け小規模ECサイト） |
| バージョン | 2.0 |
| 作成日 | 2026-08-10 |
| 目的 | 個人（ハンドメイド作家・個人事業主等）が一人で安心・簡単に運用できる、オリジナル実装のB2C ECプラットフォームを構築する |

---

## 1. プロジェクト概要

総合ECサイトの主要機能のうち、個人が一人で運営するのに十分かつ過不足のない機能だけを再実装する。コードは完全オリジナル実装とし、特定企業のブランド資産・デザイン・商標・ロゴ等は一切使用しない。UI/UXのみ「ECサイトとして使いやすい」一般的パターンを参考にする。

### 1.1 対象ユーザー
- **一般会員（購入者）**: 商品を検索・閲覧・購入する消費者
- **店主（管理者）**: 商品・在庫・注文・会員を管理する個人運営者。本プラットフォームは店主が1名であることを前提とする
- （スコープ外）複数店舗・複数管理者によるマルチテナント運用、法人向け機能拡張

### 1.2 スコープ外（明示）
- クーポン・割引キャンペーン機能（個人運営の運用負荷を下げるため意図的に非搭載。将来必要になれば別フェーズで追加）
- 複数管理者・権限段階分け（店主1名による運用を前提とするため非搭載）
- カテゴリの多段階階層（フラットな1階層のみ）
- マルチ言語対応は日本語UIを基本とし、拡張しやすい構造にする
- ネイティブアプリは対象外（レスポンシブWebのみ）

## 2. 機能要件

### 2.1 会員機能（Member）
- FR-001 会員登録（メールアドレス + パスワード、パスワードは強度チェック）
- FR-002 ログイン/ログアウト（JWTベース、アクセストークン + リフレッシュトークン）
- FR-003 プロフィール編集（氏名、電話番号、アバター）
- FR-004 パスワード変更
- FR-005 配送先住所の複数登録・編集・削除・デフォルト設定
- FR-006 会員は購入者ロール(USER)、店主は(ADMIN)ロールで権限分離。ADMINロールはseedで1件のみ作成し、会員登録経由でADMINは作成できない
- FR-007 パスワード再設定（トークン方式、未登録メールでも応答内容を同一にしアカウント存在の推測を防止）

### 2.2 商品・カタログ機能
- FR-010 カテゴリ管理(フラットな1階層のみ。名称・表示順のみを持つシンプルな構造)
- FR-011 商品一覧表示（カテゴリ別、ページネーション）
- FR-012 商品検索（キーワード、商品名/説明文全文検索）
- FR-013 商品絞り込み（カテゴリ、価格帯、在庫あり/なし）
- FR-014 商品並び替え（新着順、価格昇順/降順、売上順、評価順）
- FR-015 商品詳細ページ（画像複数枚、価格、在庫、スペック、説明、レビュー一覧、評価平均、送料の目安）。SKUは在庫管理用の内部番号のため購入者には表示しない
- FR-016 関連商品表示（同一カテゴリ内の売れ筋商品）
- FR-017 商品にSKU、ブランド、在庫数、セール価格(原価/販売価格)、消費税率を保持
- FR-021 価格はすべて税込で保持・表示すること（総額表示）。商品ごとに標準税率10%と軽減税率8%を選択でき、注文明細には購入時点の税率を控えること
- FR-018 在庫僅少バッジ表示（在庫5点以下で「残りわずか」を表示し購買意欲・在庫状況の透明性を両立）
- FR-019 割引額・割引率の明示表示（原価が設定されている商品のみ、割安感を数値で明確化）
- FR-024 最近チェックした商品の表示（閲覧履歴はブラウザ内保存、トップページに再掲し回遊率向上）
- FR-025 レビューへの購入者バッジ表示（全レビューは購入・受取確認済みのユーザーのみ投稿可能なため、検証済み社会的証明として明示）

### 2.3 カート機能
- FR-020 カートへの商品追加・数量変更・削除
- FR-021 ログイン会員のカートはDB永続化（デバイス跨ぎで同期）
- FR-022 カート内在庫チェック（在庫超過時は警告）
- FR-023 カート内合計金額のリアルタイム計算
- FR-026 送料無料までの残り金額表示（カート・チェックアウト、目標勾配効果によりAOV向上を狙う）
- FR-027 送料は届け先の都道府県による地域区分（本州・四国／九州／北海道／沖縄）で決まること。一定額以上のご購入は地域にかかわらず無料とする。確定金額は必ずサーバー側で計算し、画面表示の金額を信用しないこと

### 2.4 注文・決済機能
- FR-030 チェックアウト（配送先選択、支払方法選択：クレジットカード / PayPay / 代金引換）
- FR-031 注文確定時に在庫を確保・減算（トランザクション処理、在庫不足時は注文不可）
- FR-045 一定時間（既定60分）支払いのないオンライン決済の注文は自動的に取り消し、確保していた在庫を売り場へ戻すこと。代金引換は対象外とする。決済ページの有効期限はこの半分とし、在庫返却後に支払いが成立しないようにする。万一成立した場合は店主に通知すること
- FR-032 注文番号自動採番（一意）
- FR-033 決済代行(KOMOJU)による実決済。購入者はKOMOJUの決済ページで支払い、カード情報は当サイトを経由しない
- FR-038 注文を支払い済みにできるのは、KOMOJUから届く署名付きWebhookのみとする。購入者のブラウザからの要求では支払い済みにしない（入金がないまま発送する事故を防ぐ）
- FR-039 代金引換はKOMOJUを経由せず、支払い待ちのまま発送できる。オンライン決済の注文は入金確認前の発送を拒否する
- FR-034 注文ステータス管理：`PENDING_PAYMENT`(支払待ち) → `PAID`(支払済) → `SHIPPED`(発送済) → `COMPLETED`(受取完了) / `CANCELLED`(キャンセル) / `REFUNDED`(返金済)
- FR-035 注文履歴一覧・詳細閲覧
- FR-046 発送時に配送業者と追跡番号を記録できること。追跡番号を出せない発送方法（定形外郵便等）もあるため任意とし、未入力でも発送できること。記録した場合は、注文詳細と発送メールに番号と配送業者の追跡ページへのリンクを表示する（対応表は `backend/src/config/carrier.ts` と `frontend/assets/js/carrier.js` の両方を一致させて管理する）
- FR-036 支払待ち注文のキャンセル（在庫を復元）。購入者による取り消し・店主による取り消し・期限切れによる自動取り消しのいずれの経路でも在庫を戻すこと
- FR-037 受取完了後のレビュー投稿導線

### 2.5 レビュー・評価機能
- FR-040 購入済み商品へのレビュー投稿（評価1〜5 + コメント + 画像）
- FR-041 商品ごとの平均評価・レビュー件数の集計表示
- FR-042 不適切レビューの店主削除

### 2.6 お気に入り（ウィッシュリスト）機能
- FR-050 商品のお気に入り登録・解除・一覧表示

### 2.7 管理者（店主）機能
- FR-070 ダッシュボード（売上サマリ、注文数、会員数、在庫アラート）
- FR-071 商品管理（CRUD、写真のアップロード、公開/非公開切替、在庫調整）
- FR-078 商品写真は管理画面から直接アップロードできること。受け付けるのは先頭バイトで画像と確認できたJPEG/PNG/GIF/WebPのみとし、スクリプトを埋め込めるSVGは拒否する。JPEGのEXIF等のメタデータは保存時に除去し、撮影場所から運営者の住所が推測されないようにする
- FR-072 カテゴリ管理（CRUD。フラットな1階層のみ）
- FR-073 注文管理（一覧・検索・詳細、ステータス変更＝発送処理等）
- FR-074 会員管理（一覧・検索・凍結/解除）
- FR-075 レビュー管理（一覧・削除）
- FR-076 店主操作は全てADMINロールのみ許可（RBAC）。管理画面から新たな管理者を作成する機能は提供しない

### 2.8 請求書・領収書
- FR-110 お支払いが完了した注文について、購入者が領収書を表示・印刷できること
- FR-111 消費税は税込価格から割り戻し、税率ごとに区分した金額と消費税額を記載すること。端数処理は税率ごとに書類1枚につき1回だけ行うこと（明細行ごとに処理しないこと）
- FR-112 軽減税率の対象品目は書類上で明示すること
- FR-113 適格請求書として発行するのは、適格請求書発行事業者の登録番号が設定されている場合のみとすること。未設定の場合は領収書として発行し、適格請求書ではない旨を明記すること（免税事業者は適格請求書を発行できないため）

### 2.9 通知機能
- FR-100 注文確定時、購入者へ注文内容の控えをメールで送信する
- FR-101 支払い完了時、店主へ新規注文を知らせるメールを送信する（管理画面を開かなくても注文に気づけるようにする）
- FR-102 発送時、購入者へ発送を知らせるメールを送信する。配送業者と追跡番号が記録されている場合は、番号と追跡ページのURLを本文に含める
- FR-103 パスワード再設定の申請時、再設定リンクをメールで送信する
- FR-104 メール送信の失敗は注文・支払い・発送の成否に影響させないこと。SMTP未設定の状態でもサイトは通常どおり利用できること
- FR-105 店主宛の通知には購入者のアドレスを返信先(Reply-To)として設定し、メールソフトからそのまま返信できること。購入者宛のメールには問い合わせ先アドレスを返信先として設定すること
- FR-106 送信ドメイン認証（SPF / DKIM / DMARC）の設定状況を確認するコマンドを提供すること。差出人ドメインのDNSを実際に参照し、不足しているレコード・無効な設定（SPFの重複、参照回数の超過、`+all`、DKIM公開鍵の失効、DMARC未設定）と、その直し方を日本語で示すこと
- FR-107 差出人アドレス(`MAIL_FROM`)に無料メールのドメインが設定されている場合は、受信側で拒否されるため、確認コマンドで要対応として報告すること
- FR-108 DKIM署名を送信サービスに任せられない環境のために、アプリ側で署名する設定を用意すること（既定では無効）
- FR-109 購入者向けサイトは、APIと同じドメインで配信する構成を既定とし、公開前の設定変更なしで動作すること（別ドメインで配信する場合のみ設定を変更する）

### 2.10 共通機能
- FR-080 特定商取引法に基づく表示ページ（日本国内でのEC事業運営に必要な法定表示。個人事業主が所在地・電話番号を「請求時に遅滞なく開示」とする場合の記載例を含む。フッターから常時アクセス可能）
- FR-081 プライバシーポリシーページ。取得する情報・利用目的・外部への委託先・ブラウザに保存する情報・開示や削除の請求方法を、実装が実際に行っている処理と一致する内容で記載すること
- FR-082 利用規約ページ。売買契約の成立時期、支払方法、支払期限を過ぎた注文の自動取り消し、送料、返品・キャンセル、レビュー投稿の条件を記載すること。自動取り消しの時間や送料は設定値と一致させること
- FR-083 プライバシーポリシー・利用規約はフッターから常時アクセスでき、会員登録画面からも参照できること
- FR-090 レスポンシブ対応（PC/タブレット/スマホ、幅375px程度の狭小画面でも横スクロールが発生しないこと。ヘッダー検索欄は小画面では2段目に折り返して表示）。購入者向け画面・管理画面のいずれも、タッチ操作のみで全機能を利用できること（ホバー前提のUIを置かない）
- FR-091 エラーページ（404/500/権限エラー）
- FR-092 予期しないフロントエンド例外発生時もアプリ全体を巻き込まず復旧導線を表示（エラーバウンダリ）

## 3. 非機能要件

### 3.1 セキュリティ
- NFR-001 パスワードはbcryptでハッシュ化して保存（平文保存禁止）
- NFR-002 認証はJWT（アクセストークン短命 + リフレッシュトークン）、Authorizationヘッダで送受信
- NFR-003 全APIでZodによる入力バリデーションを実施し、不正入力を拒否
- NFR-004 ORMのパラメータバインディングによりSQLインジェクションを防止（生SQL文字列結合禁止）
- NFR-005 Helmetによるセキュリティヘッダ付与、CORS許可オリジンを明示的に限定
- NFR-006 認証系・注文系エンドポイントにレート制限を適用しブルートフォース対策（注文APIは会員単位で別枠の厳しい制限）
- NFR-007 店主向けAPIはロールベースアクセス制御(RBAC)ミドルウェアで保護
- NFR-008 機微情報（パスワードハッシュ等）はAPIレスポンスに含めない
- NFR-009 環境変数(.env)による秘密情報管理、リポジトリにシークレットをコミットしない
- NFR-012 パスワード再設定トークンはハッシュ化して保存・有効期限30分・使い切り（再利用不可）とし、メールアドレスの登録有無を応答から推測できないようにする
- NFR-015 会員アカウント凍結時は既存の全リフレッシュトークンを即時失効させ、以後の更新リクエストも拒否する（凍結の実効性を担保。既発行のアクセストークンはJWTの性質上、短い有効期限が切れるまでの最大15分間は失効しない設計上の許容リスクとする）

### 3.2 信頼性・整合性
- NFR-010 注文確定〜在庫減算はDBトランザクションで原子性を保証
- NFR-011 在庫はマイナスにならないよう楽観ロック/条件付き更新で防止
- NFR-019 決済Webhookは署名(HMAC-SHA256)を生のリクエストボディに対して検証し、一致しないものを拒否すること。通知された金額が注文額と異なる場合は反映しないこと。同一通知の再送で二重に処理しないこと
- NFR-018 注文のステータス遷移（支払い・キャンセル・受取確認・発送）は、遷移元ステータスを更新条件に含めた条件付き更新で行い、二重クリックや通信リトライで同じ処理が複数回成立しないこと。特に支払い処理は、実決済ゲートウェイに差し替えた際に多重課金とならないこと。キャンセル時の在庫復元は、状態遷移に成功したリクエストのみが実行すること
- NFR-016 チェックアウトはカート単位で排他制御（行ロック）し、二重クリック等による同一カートからの多重注文成立を防止する
- NFR-017 カート内商品が販売終了・在庫不足になった場合、購入者はチェックアウト画面に進む前にカート画面で明示され、レジに進むボタンは無効化される
- NFR-013 金額の算出は円未満の端数が生じないよう丸め処理を行い、フロント表示とバックエンド確定額を一致させる
- NFR-014 バックエンドで想定外の例外（uncaughtException/unhandledRejection）を捕捉しログ出力のうえ安全に終了する

### 3.3 性能
- NFR-020 一覧系APIはページネーション必須（大量データでも応答性維持）
- NFR-021 検索・絞り込みに使うカラムにDBインデックスを付与
- NFR-022 更新頻度の低い公開系API（カテゴリ一覧）はCache-Controlヘッダにより短時間キャッシュしサーバー負荷を軽減
- NFR-024 フロントエンドは外部CDN・外部画像サービスに依存しないこと。スタイルは生成済みCSSを自リポジトリから配信し、商品画像が未登録の場合のプレースホルダも埋め込みで表示する（外部サービスの障害でサイトの体裁が崩れたり、表示が遅くなったりしないこと）
- NFR-025 レート制限は「1人が通常の閲覧を続けても到達しない」水準とすること。リバースプロキシ配下では `TRUST_PROXY` により訪問者のIPを正しく識別し、制限が訪問者単位で機能すること（未設定だとサイト全体で1つの枠を共有し、アクセス集中時に全員が締め出される）

### 3.4 保守性・拡張性
- NFR-030 TypeScriptによる型安全な実装（バックエンド）
- NFR-031 レイヤードアーキテクチャ（routes / services / prisma）で関心分離
- NFR-032 Prisma ORMによるスキーマ管理・マイグレーション
- NFR-033 npmスクリプトによりローカル/本番環境のセットアップ手順を統一（`npm install` → `prisma migrate` → `npm run build`/`start`）

### 3.5 可用性・運用性
- NFR-040 ヘルスチェックエンドポイント `/api/health`（liveness: プロセス応答確認）/ `/api/health/ready`（readiness: DB疎通確認込み）
- NFR-041 サーバーエラーは統一エラーハンドラでログ出力・一貫したJSON形式で応答
- NFR-042 本番構成の設定ファイル（HTTPSを含むリバースプロキシ設定、プロセス常時起動の設定、バックアップの取得と復元）をリポジトリに同梱し、店主が手順どおりに実行すれば公開できること
- NFR-043 APIプロセスは異常終了後に自動で再起動し、サーバー再起動後も自動で起動すること
- NFR-044 購入者向けサイトはHTTPSで配信し、HTTPでのアクセスはHTTPSへ転送すること。リバースプロキシは商品写真のアップロード上限（5MB）を通せる本文サイズ上限を設定すること
- NFR-045 バックアップはデータベースと商品写真(`backend/uploads/`)を同時に取得し、取得したファイルが読み取り可能であることを確認すること。復元手段を提供し、本番に影響を与えずに復元を試せること（保持期間を過ぎた古いバックアップの削除は、残るバックアップが存在する場合のみ行う）
- NFR-046 本番として起動する際は設定を点検し、秘密鍵が設定例のままなど致命的な誤りがある場合は起動を中止すること。商品写真のURLの基点(`PUBLIC_API_URL`)のように、誤った状態で保存すると後から訂正できない設定は警告として知らせること

## 4. システム構成（アーキテクチャ）

```
[ブラウザ]
   │  HTTPS
   ▼
[Frontend: 素のHTML + CSS + JavaScript (ESモジュール、CSSは生成済みを同梱)] (静的配信 / port 5173 相当)
   │  REST API (JSON, fetch)
   ▼
[Backend: Node.js + Express + TypeScript] (port 4000)
   │  Prisma ORM          ├── SMTP（注文・発送・パスワード再設定の通知）
   │                      └── KOMOJU（クレジットカード / PayPay。決済ページへ遷移し、
   ▼                                   入金確定は署名付きWebhookで受け取る）
[PostgreSQL 16]
```

- 認証: JWT（Bearer Token）
- API形式: REST / JSON
- 実行方式: Docker等のコンテナ基盤に依存せず、Node.js/PostgreSQLをホストに直接インストールして `npm run dev` / `npm run build` & `npm start` で起動

## 5. データモデル（ER概要）

- **User** 1---N **Address**
- **User** 1---1 **Cart** 1---N **CartItem** N---1 **Product**
- **User** 1---N **Order** 1---N **OrderItem** N---1 **Product**
- **User** 1---N **Review** N---1 **Product**
- **User** 1---N **Wishlist** N---1 **Product**
- **Category** 1---N **Product**（フラットな1階層。自己参照なし）
- **Order** N---1 **Address**（配送先スナップショット）

クーポン・バナーに関するモデルは廃止済み。詳細カラムは `backend/prisma/schema.prisma` を正とする。

## 7. API設計方針

- ベースパス: `/api`
- 認証: `Authorization: Bearer <accessToken>`
- レスポンス統一形式: `{ success: boolean, data?: T, error?: { code, message } }`
- 主要エンドポイント群: `/auth`, `/products`, `/categories`, `/cart`, `/orders`, `/reviews`, `/wishlist`, `/addresses`, `/admin/*`
- 詳細は各routerファイルの実装を正とする

## 8. 受け入れ基準（Definition of Done）

- 会員登録→ログイン→商品閲覧→カート追加→チェックアウト→注文完了→注文履歴確認の一連のフローが動作すること
- 店主が商品・カテゴリ・注文をCRUDできること
- 主要APIに認証・認可・入力バリデーションが効いていること
- README記載の手順（PostgreSQL起動 → `npm install` → `prisma migrate` → `npm run seed` → `npm run dev`）でバックエンド・フロントエンドがローカルで起動しシステムが利用可能になること
